# 智颐云养老系统需求文档

> 版本：V1.0  
> 状态：毕业设计立项稿  
> 适用范围：后台管理端、家属端微信小程序、后端服务  
> 建设原则：保留原系统业务，前后端接口路径不变，基于 RuoYi-Geek 进行技术升级与 UI 翻新

## 1. 项目背景

### 1.1 建设背景

原智能养老系统基于 RuoYi 3.8.8 建设，已经形成后台管理与家属端微信小程序两部分能力。系统覆盖老人档案、床位、入住、合同、预约、健康评估、护理计划和护理任务等养老院日常业务。

原项目主要存在以下问题：

1. 后端技术版本较旧，与现代 Java 技术栈存在明显代差。
2. 管理端和家属端视觉风格不统一，品牌信息仍为旧名称。
3. 部分业务数据使用冗余字段或字符串保存，长期扩展和统计能力有限。
4. 数据库结构变更缺少统一版本化迁移机制。
5. 原有测试、部署、接口和数据库文档不完整。

本次毕业设计以 RuoYi-Geek 为技术基础，对原系统进行迁移、重构和品牌升级，形成“智颐云养老”系统。

### 1.2 建设目标

1. 完整保留原系统业务功能，不改变已有接口路径和主要请求字段。
2. 将后端升级到 RuoYi-Geek 的 Java 21、Spring Boot 3.5.x、MyBatis-Flex 和 Liquibase 技术体系。
3. 将管理端统一升级为 RuoYi-Geek Vue 3 管理端。
4. 重建家属端微信小程序源代码，保持原有家属端业务接口不变。
5. 统一品牌名称、视觉规范、组件风格和交互反馈。
6. 优化数据库索引、约束和关键查询，形成可追踪的迁移脚本。
7. 补齐需求、原型、技术选型、数据库、接口和改造实施文档。

### 1.3 范围边界

本期必须完成：

- 系统管理、老人档案、床位房型、入住合同、健康评估、护理计划、护理任务、预约、家属绑定和 AI 助手等原有业务。
- 后台管理端与家属端小程序的品牌和 UI 翻新。
- RuoYi-Geek 基础模块与原业务模块的整合。
- 数据库索引、约束和迁移脚本优化。

本期不建设：

- 微服务、服务注册中心、分布式事务和 Kubernetes 集群。
- 医疗诊断功能。AI 助手只提供信息查询、业务辅助和规则型提示，不替代医生诊断。
- 与养老业务无关的电商、直播、社交和复杂营销功能。

## 2. 用户角色

| 角色 | 使用端 | 主要职责 |
| --- | --- | --- |
| 超级管理员 | 后台管理端 | 管理全局配置、机构、角色、菜单、字典和系统监控 |
| 养老机构管理员 | 后台管理端 | 管理本院老人、床位、合同、护理计划和服务人员 |
| 护理主管 | 后台管理端 | 制定护理等级和计划，分配护理任务，处理超时和异常任务 |
| 护理员 | 后台管理端，后续可扩展移动端 | 查看并执行本人护理任务，填写执行记录和上传图片 |
| 健康评估人员 | 后台管理端 | 录入健康评估、维护风险等级和评估结论 |
| 前台接待人员 | 后台管理端 | 处理参观、探访预约和到访状态 |
| 家属用户 | 微信小程序 | 绑定老人、查看健康和服务信息、预约探访、查看订单与合同 |
| AI 助手服务 | 后台服务 | 按授权查询老人基础信息、健康信息和当日预约信息 |

## 3. 功能需求

### 3.1 必须保留的功能

#### FR-01 系统管理

保留 RuoYi 原有系统管理能力：

- 用户、角色、部门、岗位、菜单、字典、参数、通知公告。
- 登录日志、操作日志、在线用户、缓存和服务器监控。
- 文件上传、下载和基础文件信息管理。

验收要求：

- `sys_*` 系列表和管理接口保持兼容。
- `/login`、`/getInfo`、`/getRouters`、`/system/*` 路径不变。
- 原角色权限标识继续生效。

#### FR-02 老人档案管理

保留老人基本信息维护能力：

- 姓名、性别、身份证号、手机号、出生日期、家庭住址。
- 身份证正反面图片、床位和状态。
- 老人新增、修改、删除、详情、列表和 Excel 导出。

保留接口：

- `GET /nursing/elder/list`
- `GET /nursing/elder/{id}`
- `POST /nursing/elder`
- `PUT /nursing/elder`
- `DELETE /nursing/elder/{ids}`
- `POST /nursing/elder/export`

验收要求：

- 原老人状态编码含义不变。
- 老人列表查询性能不低于原系统。
- 身份证号、手机号等敏感信息按权限展示。

#### FR-03 楼层、房间、房型和床位管理

保留楼层、房型、房间和床位结构：

- 楼层维护。
- 房型维护。
- 房间和床位状态维护。
- 小程序端房型查询。

保留接口：

- `/nursing/floor/*`
- `/nursing/room/*`
- `/nursing/roomType/*`
- `/nursing/bed/*`
- `/member/roomTypes`

验收要求：

- 床位状态仍使用“未入住、已入住、入住申请中”的原编码。
- 小程序房型接口路径和返回结构保持兼容。

#### FR-04 入住与合同管理

保留入住申请、入住详情、合同创建和状态更新：

- 校验老人是否已入住。
- 更新床位状态。
- 新增或更新老人。
- 创建合同和入住配置。
- 更新健康评估入住状态。

保留接口：

- `GET /nursing/checkIn/detail/{id}`
- `POST /nursing/checkIn/apply`
- `/nursing/checkIn/*`
- `/nursing/contract/*`

验收要求：

- 入住申请使用事务，任何步骤失败均回滚。
- 合同编号唯一。
- 已入住老人在未退住前不可重复办理入住。

#### FR-05 健康评估管理

保留健康评估和评估详情：

- 评估编号、老人姓名、身份证号、健康评分、评估时间。
- 风险等级、报告总结和评估明细。
- 入住状态联动。

保留接口：

- `/nursing/healthAssessment/*`

验收要求：

- 健康数据只作为护理参考，不显示医疗诊断结论。
- 家属端只能查看与已绑定老人相关的信息。

#### FR-06 护理等级、项目、计划与任务

保留护理业务主链路：

- 护理等级维护。
- 护理项目维护。
- 护理计划与项目关联。
- 按日、周、月生成护理任务。
- 护理任务查询、改期、取消、执行和删除。

保留接口：

- `/nursing/nursingLevel/*`
- `/nursing/project/*`
- `/nursing/nursingPlan/*`
- `/nursing/nursingTask/*`

验收要求：

- 任务生成规则与原系统一致。
- 同一老人、项目和计划时间不应生成完全重复的任务。
- 执行任务后记录实际服务时间、执行记录和图片。

#### FR-07 预约管理

保留参观预约、探访预约、到访状态和取消规则：

- 同一时段最多 6 条预约。
- 同一手机号在同一时段只能预约一次。
- 预约状态包括待报道、已完成、取消和过期。
- 支持按日统计和分页查询。

保留接口：

- `/nursing/reservation/*`
- `/member/reservation`
- `/member/reservation/countByTime`
- `/member/reservation/cancelled-count`
- `/member/reservation/page`
- `/member/reservation/{id}/cancel`

验收要求：

- 并发提交时预约上限规则不能失效。
- 取消操作记录更新人。
- 过期待处理预约由定时任务更新。

#### FR-08 家属端绑定与查询

保留家属端业务：

- 家属登录。
- 绑定、解绑老人。
- “我的家人”列表。
- 分页查询家属与老人关联记录。
- 查看老人基础信息、健康信息、护理项目、订单、账单和合同。

保留接口：

- `POST /member/user/login`
- `POST /member/user/add`
- `GET /member/user/my`
- `GET /member/user/list-by-page`
- `DELETE /member/user/deleteById`

验收要求：

- 家属只能访问已绑定老人数据。
- 解绑后不得继续缓存老人敏感信息。
- 401 时清除本地 Token 并返回登录页。

#### FR-09 AI 助手

保留现有 Dify 流式对话能力：

- 老人基本信息查询。
- 老人健康信息查询。
- 当日预约查询。
- 对话历史删除。

保留接口：

- `POST /ai/chat`
- `GET /ai/history`
- `GET /ai/history/{chatId}`
- `DELETE /ai/history/{chatId}`
- `/dify/serve/*`

验收要求：

- AI 不直接访问数据库，通过业务接口查询。
- 流式响应中断时前端能够恢复输入状态。
- Dify Token 不得写入前端或 Git 仓库。

### 3.2 建议新增的功能

#### FR-N1 护理任务超时提醒

新增价值：

- 现有护理任务已经包含预计服务时间和状态，可直接计算超时任务。
- 对护理主管和护理员具有明确业务价值，不需要复杂算法。

功能范围：

- 任务看板展示待执行、今日执行、已超时、已关闭数量。
- 预计服务时间超过阈值且状态仍为待执行时生成提醒。
- 支持机构管理员查看，不改变原护理任务接口。

#### FR-N2 家属服务进度

新增价值：

- 家属可查看最近护理服务记录、下一次预约和健康摘要。
- 复用现有护理任务、预约和健康评估数据，不新增独立业务链路。

功能范围：

- 小程序首页显示老人当前入住状态、护理等级、最近健康评分。
- 显示最近一次护理服务和下一次预约。
- 只读展示，不提供家属修改护理计划的入口。

#### FR-N3 规则型风险提示（后续预留）

首期不在界面正式开放风险提示功能，只预留 `care_alert_rule` 和 `care_alert` 数据结构与接口边界。健康评分、风险等级、护理任务超时和合同到期仍作为后续扩展依据，避免在毕业设计阶段引入未确认的医学规则。

### 3.3 建议舍弃的内容

以下内容不进入新系统：

| 内容 | 处理方式 | 原因 |
| --- | --- | --- |
| 旧系统页面主题和静态 Logo | 舍弃并重做 | 与“智颐云养老”品牌不一致 |
| 旧权限框架和重复认证代码 | 舍弃，使用 RuoYi-Geek 内置实现 | 避免两套安全框架并存 |
| 明文数据库、Redis、OSS、Dify 密钥 | 从源码和仓库移除 | 存在严重安全风险 |
| 编译后的小程序产物 | 不作为源码长期维护 | 可读性和可维护性差 |
| 无业务用途的演示菜单 | 隐藏或删除菜单数据 | 影响评审和操作体验 |
| 重复或失效的 SQL 初始化脚本 | 归档，不继续执行 | 防止数据库状态不可追踪 |

注意：舍弃的是旧实现、旧样式和无用数据，不是舍弃对应业务能力。

## 4. 非功能需求

### 4.1 性能

| 编号 | 要求 |
| --- | --- |
| NFR-P1 | 常规查询接口本地环境 P95 小于 500ms |
| NFR-P2 | 分页接口默认每页 10 条，单页最大 100 条 |
| NFR-P3 | 老人列表、护理任务、预约查询必须使用索引 |
| NFR-P4 | 护理任务生成使用批量插入，禁止逐条远程请求 |
| NFR-P5 | 静态资源启用压缩和缓存，图片使用 WebP 或 AVIF |

### 4.2 安全

| 编号 | 要求 |
| --- | --- |
| NFR-S1 | 管理员和家属端均使用 JWT 鉴权 |
| NFR-S2 | 密码使用 BCrypt，禁止明文或 MD5 存储 |
| NFR-S3 | 接口权限使用 Spring Security 和权限标识 |
| NFR-S4 | 家属端必须校验老人绑定关系 |
| NFR-S5 | 数据库、Redis、OSS、微信和 Dify 密钥使用环境变量 |
| NFR-S6 | 关键操作写入操作日志 |
| NFR-S7 | 登录、预约、AI 对话等高频接口支持限流 |

### 4.3 可用性与无障碍

- 正文默认字号不低于 16px。
- 触控目标不小于 44 x 44px。
- 正常文本对比度不低于 4.5:1。
- 所有表单提供可见标签、错误提示和键盘焦点样式。
- 尊重系统“减少动态效果”设置。
- 小程序支持常见手机宽度和横屏基本可用。

### 4.4 可维护性

- 使用 Maven 多模块管理后端。
- 使用 Vue 3、TypeScript 和组合式 API。
- 数据库结构使用 Liquibase 管理。
- 新功能先写接口约定，再实现前后端。
- 业务代码不得在 Controller 中直接编写复杂 SQL。

### 4.5 兼容性

- 保持原接口路径、请求方法、主要参数名和返回字段。
- 旧数据迁移后，状态编码和历史业务数据继续可读。
- 管理端支持 Chrome、Edge 当前稳定版本。
- 小程序基于微信开发者工具和体验版进行验收。

### 4.6 部署与外部服务

- 本地开发运行在 Windows，MySQL、Redis、Dify 和 RAGFlow 部署在 Linux VM。
- 最终后端、管理端、MySQL 和 Redis 部署到 `192.168.100.168`。
- Dify 和 RAGFlow 部署在 `192.168.100.128`，通过局域网访问。
- 小程序只做局域网联调，不配置公网域名和正式 HTTPS。
- 文件存储支持本地磁盘和阿里云 OSS，未配置 OSS 参数时自动回退本地。
- AI 对话和知识检索由 Dify 统一编排，RAGFlow 只作为知识检索后端。

## 5. 业务流程

### 5.1 老人入住流程

```text
家属预约
  -> 前台核验与到访
  -> 健康评估
  -> 选择房型、房间和床位
  -> 提交入住申请
  -> 创建合同、入住记录和入住配置
  -> 更新床位和健康评估状态
  -> 生成护理任务
```

### 5.2 护理任务流程

```text
维护护理项目
  -> 配置护理计划
  -> 老人绑定护理等级和计划
  -> 定时任务生成待执行任务
  -> 护理员执行或改期
  -> 记录服务结果
  -> 主管查看统计与超时提醒
```

### 5.3 家属端流程

```text
微信登录
  -> 绑定老人
  -> 查看老人基础信息与健康摘要
  -> 查看护理服务进度
  -> 提交参观或探访预约
  -> 查看预约、订单、账单和合同
```

## 6. 验收标准

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-01 | 原接口兼容 | 原有前端关键接口无需修改路径和方法即可调用 |
| AC-02 | 系统管理 | 用户、角色、菜单、字典、日志功能正常 |
| AC-03 | 老人业务 | 老人、床位、入住、合同、健康评估全流程可完成 |
| AC-04 | 护理业务 | 护理计划可生成任务，任务可执行、改期和取消 |
| AC-05 | 预约业务 | 时段上限、手机号限制、取消和过期状态均正确 |
| AC-06 | 家属端 | 可登录、绑定老人、查询信息和提交预约 |
| AC-07 | AI 助手 | 可流式返回结果，历史记录可查询和删除 |
| AC-08 | 品牌升级 | 所有用户可见页面统一显示“智颐云养老” |
| AC-09 | 数据库迁移 | Liquibase 可从空库完整初始化，并能增量升级 |
| AC-10 | 安全 | 仓库中不存在真实密钥，权限和绑定校验有效 |
| AC-11 | UI/UX | 桌面端和手机端无横向溢出，关键操作有明确反馈 |
| AC-12 | 可部署性 | 后端、管理端、小程序可按文档独立启动和部署 |
