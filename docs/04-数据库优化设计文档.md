# 智颐云养老系统数据库优化设计文档

> 版本：V1.0  
> 数据库：MySQL 8.0  
> 迁移工具：Liquibase  
> 核心原则：表名和既有字段优先保持不变，新增字段采取兼容式扩展，禁止直接重命名或删除业务字段

最终数据库 schema 名称为 `zyyyl`。原 `zzyl/sql/zzyl.sql` 同时包含建表语句和业务数据，本项目只提取 DDL、字典和必要的脱敏演示数据，不迁移真实老人、家属和合同记录。

## 1. 原数据库结构分析

### 1.1 表结构来源

本文档基于以下信息整理：

- RuoYi-Geek 的 Liquibase 变更文件。
- 原 `zzyl` 项目的 Domain 实体类。
- 原 `zzyl` 项目的 Mapper XML 和 Service 查询逻辑。
- 原管理端和小程序接口调用。

由于当前仓库缺少一份完整、最终版本的 SQL DDL，字段长度、默认值、注释和部分索引仍需在数据库备份中核对，并在本文档中标记为“待确认”。

### 1.4 主要问题

| 问题 | 典型位置 | 影响 |
| --- | --- | --- |
| 逗号分隔多值 | `nursing_task.nursing_id` | 不符合第一范式，难以按护理员统计 |
| JSON 存入备注字段 | `check_in.remark` 保存家属列表 | 查询和校验困难 |
| 缺少唯一约束 | 合同编号、家属老人关联、床位编号 | 可能产生重复业务数据 |
| 缺少组合索引 | 预约时间、任务状态、健康评估时间 | 数据量增长后查询变慢 |
| 冗余名称字段 | 老人姓名、床位编号、护理等级名称 | 有利于历史追踪，但需明确同步规则 |
| 时间字段类型不统一 | `elder.birthday` 为字符串 | 比较、年龄统计和迁移不方便 |
| 业务外键缺失 | 多数关联表未声明外键 | 可能出现孤儿数据 |
| 分页和查询依赖大量内存过滤 | 原 Service 部分逻辑 | 大数据量下性能不稳定 |

## 2. 优化目标与原则

### 2.1 目标

1. 保持原表名、原字段和原接口兼容。
2. 为核心查询增加索引和约束。
3. 将逗号分隔和 JSON 数据逐步拆分为关系表。
4. 增加护理超时和风险提示所需的轻量级数据表。
5. 所有结构改动通过 Liquibase 变更集执行。
6. 支持备份、回滚和数据一致性校验。

### 2.2 原则

- 第一阶段只做新增字段、索引和新表，不重命名、不删除旧字段。
- 唯一约束必须先去重，再上线。
- 历史名称字段允许保留，但必须记录更新时间。
- 外键约束先用于新表；旧表在历史脏数据清理后再增加。
- 所有时间使用 `DATETIME`，日期使用 `DATE`，金额使用 `DECIMAL`。
- 所有业务表包含 `create_by`、`create_time`、`update_by`、`update_time` 和 `remark`，与 RuoYi 规范一致。

## 3. 表结构优化方案

### 3.1 老人表 `elder`

已有核心字段：

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGINT` | 主键 |
| `name` | `VARCHAR(64)` | 姓名 |
| `image` | `VARCHAR(512)` | 头像或照片地址 |
| `id_card_no` | `VARCHAR(18)` | 身份证号，待确认是否允许空 |
| `sex` | `TINYINT` | 0 女，1 男 |
| `status` | `TINYINT` | 0 禁用，1 启用，2 请假，3 退住中，4 入住中，5 已退住 |
| `phone` | `VARCHAR(20)` | 手机号 |
| `birthday` | `DATE` 或 `VARCHAR(32)` | 原字段可能为字符串，迁移前需核对 |
| `address` | `VARCHAR(255)` | 家庭住址 |
| `id_card_national_emblem_img` | `VARCHAR(512)` | 身份证国徽面 |
| `id_card_portrait_img` | `VARCHAR(512)` | 身份证人像面 |
| `bed_number` | `VARCHAR(64)` | 床位编号快照 |
| `bed_id` | `BIGINT` | 当前床位 ID |

建议新增：

| 新增字段 | 类型 | 说明 |
| --- | --- | --- |
| `nursing_level_id` | `BIGINT NULL` | 当前护理等级 ID |
| `last_assessment_id` | `BIGINT NULL` | 最近一次健康评估 ID |
| `emergency_contact` | `VARCHAR(64) NULL` | 紧急联系人 |
| `emergency_phone` | `VARCHAR(20) NULL` | 紧急联系电话 |
| `check_in_status` | `TINYINT NULL` | 即将入住、已入住、退住中等扩展状态 |

索引建议：

```sql
CREATE INDEX idx_elder_status_bed ON elder(status, bed_id);
CREATE INDEX idx_elder_name ON elder(name);
CREATE INDEX idx_elder_phone ON elder(phone);

-- 待确认：清理重复身份证后再执行
CREATE UNIQUE INDEX uk_elder_id_card ON elder(id_card_no);
```

注意：

- 历史数据中身份证号可能为空或重复，不能直接增加唯一索引。
- 姓名允许重复，不设置唯一约束。

### 3.2 楼层、房间、房型和床位

推荐关系：

```text
floor 1 --- n room
room_type 1 --- n room
room 1 --- n bed
elder 1 --- 0..1 current bed
```

建议索引：

```sql
CREATE INDEX idx_room_floor ON room(floor_id);
CREATE INDEX idx_room_room_type ON room(room_type_id);
CREATE INDEX idx_bed_room ON bed(room_id);
CREATE INDEX idx_bed_status_room ON bed(bed_status, room_id);
CREATE UNIQUE INDEX uk_bed_number ON bed(bed_number);
```

说明：

- `bed_number` 是否全局唯一需结合原系统编号规则确认。
- 床位状态保持 0 空闲、1 已入住、2 入住申请中的原编码。

### 3.4 合同表 `contract`

建议约束和索引：

```sql
CREATE UNIQUE INDEX uk_contract_number ON contract(contract_number);
CREATE INDEX idx_contract_elder_status ON contract(elder_id, status);
CREATE INDEX idx_contract_end_status ON contract(end_date, status);
CREATE INDEX idx_contract_sign_date ON contract(sign_date);
```

规则：

- `contract_number` 为合同编号，必须唯一。
- 同一老人允许存在多份历史合同，但同一时间只能有一份有效主合同。
- 删除合同优先逻辑删除，保留审计价值。

护理任务表建议新增：

| 新增字段 | 类型 | 说明 |

| `plan_id` | `BIGINT NULL` | 来源护理计划 |
| `source_type` | `TINYINT DEFAULT 1` | 自动生成、手工新增 |
| `timeout_status` | `TINYINT DEFAULT 0` | 0 正常，1 已超时，2 已处理 |
| `version` | `INT DEFAULT 0` | 乐观锁版本 |

索引建议：

```sql
CREATE UNIQUE INDEX uk_nursing_task_no ON nursing_task(task_no);
CREATE INDEX idx_task_elder_status_time ON nursing_task(elder_id, status, estimated_server_time);
CREATE INDEX idx_task_status_time ON nursing_task(status, estimated_server_time);
CREATE INDEX idx_task_project_time ON nursing_task(project_id, estimated_server_time);
CREATE INDEX idx_task_timeout ON nursing_task(timeout_status, estimated_server_time);
```

防重复任务建议：

```sql
CREATE UNIQUE INDEX uk_task_unique
ON nursing_task(elder_id, project_id, estimated_server_time, source_type);
```

注意：

- 执行前必须先清理历史重复任务。
- 人工补录或同一时间多项同类任务是否允许重复，需要业务确认。

### 3.7 预约表 `reservation`

保留字段：

- `name`
- `mobile`
- `time`
- `visitor`
- `type`
- `status`

建议索引：

```sql
CREATE INDEX idx_reservation_time_status ON reservation(time, status);
CREATE INDEX idx_reservation_mobile_time ON reservation(mobile, time);
CREATE INDEX idx_reservation_type_status ON reservation(type, status);
CREATE INDEX idx_reservation_create_time ON reservation(create_time);
```

并发控制：

- 预约总量校验和手机号重复校验必须在同一事务中执行。
- 生产环境可使用 Redis 分布式锁或数据库唯一约束辅助控制。
- 不建议直接增加 `(mobile, time)` 唯一索引，因为原业务可能允许同一手机号在同一时段预约不同类型。

待确认：同一手机号是否允许同时存在参观预约和探访预约。

CREATE INDEX idx_family_elder_family ON family_member_elder(family_member_id);

## 4. 新增表设计

### 4.1 `check_in_family`

替代 `check_in.remark` 中保存家属 JSON 的做法。

```sql
CREATE TABLE check_in_family (
  id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
  check_in_id BIGINT NOT NULL COMMENT '入住ID',
  family_name VARCHAR(64) NOT NULL COMMENT '家属姓名',
  relation VARCHAR(32) NULL COMMENT '与老人关系',
  phone VARCHAR(20) NULL COMMENT '联系电话',
  is_primary TINYINT NOT NULL DEFAULT 0 COMMENT '是否主要联系人',
  create_by VARCHAR(64) NULL,
  create_time DATETIME NULL,
  update_by VARCHAR(64) NULL,
  update_time DATETIME NULL,
  remark VARCHAR(500) NULL,
  PRIMARY KEY (id),
  KEY idx_check_in_family_main (check_in_id, is_primary),
  CONSTRAINT fk_check_in_family_check_in
    FOREIGN KEY (check_in_id) REFERENCES check_in(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='入住家属联系人';
```

迁移策略：

1. 先创建新表。
2. 解析旧 `check_in.remark` JSON。
3. 写入 `check_in_family`。
4. 新旧双读一段时间。
5. 验证一致后停止写入旧备注字段。
6. 不删除旧备注字段。

### 4.2 `nursing_task_assignee`

替代 `nursing_task.nursing_id` 的逗号分隔多值。

```sql
CREATE TABLE nursing_task_assignee (
  id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
  task_id BIGINT NOT NULL COMMENT '护理任务ID',
  nursing_id BIGINT NOT NULL COMMENT '护理员ID',
  assign_status TINYINT NOT NULL DEFAULT 0 COMMENT '0待接受 1已接受 2已完成',
  assign_time DATETIME NULL COMMENT '分配时间',
  complete_time DATETIME NULL COMMENT '完成时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_task_nursing (task_id, nursing_id),
  KEY idx_nursing_status (nursing_id, assign_status),
  CONSTRAINT fk_task_assignee_task
    FOREIGN KEY (task_id) REFERENCES nursing_task(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='护理任务执行人';
```

迁移策略：

- 将逗号字符串按逗号拆分并写入新表。
- 原字段暂时保留，兼容旧查询。
- 新接口优先读取关联表，旧字段只作为兜底。

### 4.3 `care_alert_rule`

用于配置规则型风险提示，不保存医学判断。

```sql
CREATE TABLE care_alert_rule (
  id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
  rule_code VARCHAR(64) NOT NULL COMMENT '规则编码',
  rule_name VARCHAR(128) NOT NULL COMMENT '规则名称',
  rule_type VARCHAR(32) NOT NULL COMMENT 'HEALTH、TASK、CONTRACT、RESERVATION',
  threshold_value DECIMAL(10,2) NULL COMMENT '阈值',
  threshold_unit VARCHAR(32) NULL COMMENT '阈值单位',
  severity TINYINT NOT NULL DEFAULT 1 COMMENT '1提示 2警告 3严重',
  enabled TINYINT NOT NULL DEFAULT 1 COMMENT '是否启用',
  create_by VARCHAR(64) NULL,
  create_time DATETIME NULL,
  update_by VARCHAR(64) NULL,
  update_time DATETIME NULL,
  remark VARCHAR(500) NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_care_alert_rule_code (rule_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='风险提示规则';
```

### 4.4 `care_alert`

```sql
CREATE TABLE care_alert (
  id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
  elder_id BIGINT NULL COMMENT '老人ID',
  rule_code VARCHAR(64) NOT NULL COMMENT '规则编码',
  alert_title VARCHAR(128) NOT NULL COMMENT '提示标题',
  alert_content VARCHAR(500) NOT NULL COMMENT '提示内容',
  severity TINYINT NOT NULL COMMENT '严重程度',
  source_type VARCHAR(32) NULL COMMENT '来源类型',
  source_id BIGINT NULL COMMENT '来源业务ID',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '0待处理 1已处理 2已忽略',
  handle_by VARCHAR(64) NULL COMMENT '处理人',
  handle_time DATETIME NULL COMMENT '处理时间',
  handle_remark VARCHAR(500) NULL COMMENT '处理说明',
  create_time DATETIME NULL,
  update_time DATETIME NULL,
  PRIMARY KEY (id),
  KEY idx_alert_elder_status (elder_id, status),
  KEY idx_alert_severity_status (severity, status),
  KEY idx_alert_source (source_type, source_id),
  CONSTRAINT fk_alert_elder
    FOREIGN KEY (elder_id) REFERENCES elder(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='护理风险提示';
```

生成规则示例：

- 健康评分低于规则阈值。
- 健康风险等级达到规则阈值。
- 同类护理任务连续超时。
- 合同在指定天数内到期。

## 5. Liquibase 变更示例

文件建议：

```text
zyyyl-admin/src/main/resources/db/changelog/
├─ changelog-1-master.xml
├─ changelog-4-nursing.xml
└─ changelog-5-zyyyl-migration.xml
```

增加索引：

```xml
<changeSet id="20260929-01-create-nursing-task-index" author="zhiyiyun">
    <preConditions onFail="MARK_RAN">
        <not>
            <indexExists tableName="nursing_task"
                         indexName="idx_task_elder_status_time"/>
        </not>
    </preConditions>
    <createIndex tableName="nursing_task"
                 indexName="idx_task_elder_status_time">
        <column name="elder_id"/>
        <column name="status"/>
        <column name="estimated_server_time"/>
    </createIndex>
    <rollback>
        <dropIndex tableName="nursing_task"
                   indexName="idx_task_elder_status_time"/>
    </rollback>
</changeSet>
```

新增字段：

```xml
<changeSet id="20260929-02-add-nursing-task-timeout" author="zhiyiyun">
    <preConditions onFail="MARK_RAN">
        <not>
            <columnExists tableName="nursing_task" columnName="timeout_status"/>
        </not>
    </preConditions>
    <addColumn tableName="nursing_task">
        <column name="timeout_status" type="TINYINT" defaultValueNumeric="0"
                remarks="0正常 1已超时 2已处理"/>
    </addColumn>
    <rollback>
        <dropColumn tableName="nursing_task" columnName="timeout_status"/>
    </rollback>
</changeSet>
```

说明：

- 项目实际 changeSet ID 应遵循本地已有命名规范。
- 不要在已执行的生产 changeSet 中修改内容，必须追加新 changeSet。
- 回滚脚本只用于开发和受控环境，生产回滚需先备份。

## 6. 性能优化策略

### 6.1 查询优化

1. 列表查询只返回必要字段，禁止 `SELECT *`。
2. 老人、任务、预约列表使用数据库分页。
3. 模糊搜索字段避免前置 `%` 条件。
4. 统计接口优先使用聚合 SQL，不在 Java 中加载全量数据。
5. 批量任务生成使用 `saveBatch` 或批量 SQL。
6. 任务数超过 1 万条时按月份或状态归档。

### 6.2 缓存策略

| 数据 | 缓存位置 | 建议 TTL |
| --- | --- | --- |
| 字典、参数 | Caffeine + Redis | 30 至 60 分钟 |
| 护理项目 | Caffeine + Redis | 10 至 30 分钟 |
| 房型列表 | Redis | 5 至 15 分钟 |
| 当日预约统计 | Redis | 1 至 5 分钟 |
| 老人健康摘要 | 不缓存或短缓存 | 1 分钟以内 |

涉及健康、合同和预约状态更新时，应主动清理相关缓存。

### 6.3 并发控制

| 场景 | 控制方式 |
| --- | --- |
| 床位同时申请 | 乐观锁或行锁 |
| 预约时段上限 | 事务 + 行锁或 Redis 锁 |
| 重复护理任务 | 唯一索引 + 幂等校验 |
| 合同编号 | 唯一索引 |
| 家属重复绑定 | 联合唯一索引 |

## 7. 数据迁移方案

### 7.1 迁移顺序

1. 备份原数据库，记录所有表行数。
2. 初始化 RuoYi-Geek 基础表。
3. 导入系统字典、菜单和基础参数。
4. 迁移老人、楼层、房间、床位和房型。
5. 迁移入住、合同和健康评估。
6. 迁移护理等级、项目、计划和任务。
7. 迁移预约和家属绑定。
8. 迁移文件路径和对象存储地址。
9. 建立索引和唯一约束。
10. 执行接口和数据一致性回归。

### 7.2 校验项

| 校验项 | 通过标准 |
| --- | --- |
| 表行数 | 与原库业务表一致或差值有记录 |
| 老人 ID | 原 ID 与入住、任务、预约关联一致 |
| 合同编号 | 无重复 |
| 床位占用 | 同一床位不存在两个在住老人 |
| 家属绑定 | 无重复关联 |
| 护理任务 | 无重复任务，状态编码正确 |
| 预约 | 状态、时间和手机号数据完整 |
| 文件地址 | 可访问或已迁移到新存储 |
